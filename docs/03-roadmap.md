# План этапов — Текстовая космическая MMORPG (MVP)

Версия 1.0 • 23 ноября 2026 г.
Каждый этап завершается работающим деплоем на staging и набором тестов. Критерии готовности MVP — из ТЗ, проверяются на этапе 9–10.

## Этап 0. Каркас (1 неделя) `[план]`

- Монорепо: `core/ app/ adapters/ admin/ worker/ deploy/`, CI (линт, mypy, тесты, сборка образов).
- Docker Compose: postgres, redis, app, worker, vk-adapter, admin-ui.
- Alembic-миграции, JSON-логирование с correlation id, health checks, конфигурация через env.
- `config_params`/`formulas` — инфраструктура чтения с hot-reload.
- Command Bus: per-character advisory lock, `idempotency_keys`, outbox-запись.

**Выход:** пустой бот отвечает в VK, инфраструктура деплоя staging/prod работает.

## Этап 1. Аккаунт, персонаж, фракция, инвентарь (1–2 недели) `[план]`

- `accounts`, `account_identities` (VK-привязка; Telegram — интерфейс), `characters`, `factions`, `reputations`.
- Создание персонажа: выбор фракции, выдача стартового корабля/ресурсов, проверка имён (blacklist + журнал).
- `item_templates`, `inventories`, `inventory_items`: 30 слотов, стеки, уникальные предметы.
- VK-адаптер: текстовые команды, экраны Mini App-заглушки.

**Выход:** игрок создаёт персонажа и видит инвентарь; критерий ТЗ «игрок создаёт персонажа, выбирает фракцию».

## Этап 2. Конвейер команд и защита от повторов (1 неделя) `[план]`

- Полный цикл §5.1 (architecture): идемпотентность, «занятость», outbox-диспетчер с rate limit/retry.
- Тесты на параллельные команды и повторные запросы.

**Выход:** гарантии последовательности и идемпотентности подтверждены интеграционными тестами.

## Этап 3. Космопорт, топливо, экспедиции (2 недели) `[план]`

- `expeditions`, `event_templates`, `event_tables`, `expedition_events`; генерация очереди событий.
- Топливо, трата на события, три сценария возвращения (voluntary/fuel_empty/defeat), таймер задержки, сообщения старт/прибытие, сохранение топлива.
- Офлайн-заморозка экспедиции; таймеры через `timers` + worker.

**Выход:** критерий ТЗ «экспедиция генерирует события, расходует топливо, поддерживает добровольное/автоматическое возвращение». Разграничение дроп/waiting — тесты.

## Этап 4. Пошаговый бой (2 недели) `[план]`

- `enemy_templates`, `enemy_abilities`, `loot_tables`, `battles`, `battle_turns`.
- Движок: ход игрока → ход противника (weighted-логика; пассивы/слабости elite/boss), способности/навыки/расходники, лимит расходников за ход, запрет смены модулей.
- Отступление (1 попытка, шанс из config, последствия), победа (автонаграды, опыт только за победу), поражение (потеря доли добычи по флагам, поломки, автовозврат).
- Краткий итог хода + подробный журнал по запросу; приблизительные вероятности.

**Выход:** критерий ТЗ «боевая система корректно обрабатывает ходы, способности, расходники, отступление, победу и поражение» + «потери, награды, прочность и поломки без потери/дублирования предметов».

## Этап 5. Модули и развитие (1–2 недели) `[план]`

- `module_templates`, `module_instances`, `effect_templates`; установка/снятие (прогресс сохраняется), max_per_ship.
- Распределение xp_pool на модули (только в космопорту), пересчёт характеристик корабля (база + модули + эффекты).
- Сброс распределения за спец. предмет/ресурс, формула повторных сбросов из config.
- Mini App: экран развития.

**Выход:** критерий ТЗ «игрок устанавливает и снимает модули, развивает способности и навыки».

## Этап 6. Крафт, склад, «Ожидает получения» (1–2 недели) `[план]`

- `recipe_templates`, `craft_jobs`, производственные слоты; несколько параллельных таймеров в реальном времени.
- Запуск только при полных материалах; отмена с частичным возвратом; результат в waiting при переполнении; автовозврат из waiting при освобождении места; склад (недоступен в экспедиции).

**Выход:** критерий ТЗ «крафт работает с несколькими таймерами, отменой и частичным возвратом материалов» + «инвентарь, склад и раздел ожидания работают согласованно».

## Этап 7. Экономика и торговля (2 недели) `[план]`

- `wallets`, `wallet_ledger` (reserve-причины), `eon_market_orders` + сведение worker'ом, `market_config`.
- `auction_lots`, `auction_bids`: комиссия 1%, лимиты лотов 5/10, возврат через 20 мин, запрет уникальных.
- `transfers`: лимиты/комиссии, резерв + подтверждение ценных, сроки, автоматическое исполнение обычных.
- `shop_offers`, `purchases` (идемпотентный webhook), `subscriptions` (7/30 дн., бонусы с капом 95% и затуханием).

**Выход:** критерий ТЗ «аукцион и прямая передача соблюдают комиссии, ограничения, резервы и защиту от повторных операций». Платёжный провайдер — мок до согласования (решение №8).

## Этап 8. Задания и фракционные события MVP (1–2 недели) `[план]`

- `quest_templates`, `character_quests`: обязательное первое сюжетное задание, цепочка обучения через события первой экспедиции.
- `faction_events`, `faction_event_participants`: общие цели + индивидуальный вклад; запуск по расписанию/случайно/по условиям/вручную.
- Справочник в Mini App.

## Этап 9. Админ-панель, Mini App, аудит (2 недели, частично параллельно) `[план]`

- RBAC: администратор/модератор/контент-менеджер; `audit_log`; модерация имён/банов; применение существующих эффектов.
- Редакторы: конфиги/формулы (с валидацией схемы), предметы/рецепты/враги/события/дроп, экономика/лимиты; публикация контент-менеджером в своей зоне.
- Аналитика: активные игроки, воронка обучения, обороты рынка; дашборд.
- Mini App: профиль, инвентарь/склад/waiting, развитие, крафт, справочник, боевой журнал.

**Выход:** критерий ТЗ «основные балансировочные параметры доступны через админ-панель».

## Этап 10. Тестирование, эксплуатация, релиз (2 недели) `[план]`

- Нагрузочный тест команд (цель: узкое место — per-char lock; фиксация RPS на одного игрока и в среднем).
- Балансировка на стартовых числах из config (без правок кода).
- Резервное копирование: pg_dump по расписанию + тестовое восстановление; runbook отката миграций.
- Мониторинг/алерты (Grafana/Sentry), maintenance-mode процедура, инструкции развёртывания.
- Проверка всех критериев готовности MVP из ТЗ как чек-лист релиза.

**Выход:** production-релиз MVP, runbook, инструкции запуска/миграций/бэкапа/восстановления.

## Зависимости и риски

- Этапы 1–3 — критический путь; 5–7 можно параллелить командами после этапа 4.
- Риск: платёжный провайдер не согласован → этап 7 идёт с моком, интеграция — отдельным патчем (решение №8).
- Риск: лимиты VK Long Poll при росте аудитории → переход на Callback API — внутри адаптера, ядро не затрагивается.
- Открытые числа ТЗ (баланс, таймеры, пороги) блокируют только финальную балансировку (этап 10), не архитектуру — всё в `config_params`.

## Оценка объёма

Итого ≈ 15–19 недель одной командой (2–3 разработчика). Параллельная разработка этапов 5–9 сокращает календарный срок до ≈ 12–14 недель.
